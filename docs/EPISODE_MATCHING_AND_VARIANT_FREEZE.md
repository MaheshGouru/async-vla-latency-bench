## 2. Confirmatory Horizon–Delay Operating Envelope matching rule

Confirmatory Horizon–Delay Operating Envelope uses new seeds:

```text
SEEDS = [5,6,7,8,9]
```

Therefore Confirmatory Horizon–Delay Operating Envelope episodes do **not** match Latency Calibration and Instrumentation/1 by seed.

They match Latency Calibration and Instrumentation/1 only at the level of:

```text
same checkpoint
same three base task identities
same RTC implementation
same control/timing semantics
same preprocessing/action representation
same hardware/runtime class where feasible
```

Within Confirmatory Horizon–Delay Operating Envelope, matching is strict:

> For a fixed `(task_key, seed)`, every horizon × delay condition must begin from
> the same base-task initialization generated by that seed, to the extent the
> environment API is deterministic.

Thus for one task and seed, all of:

```text
n_action_steps = 10,15,20,25,30,35
delay = Native,+100,+200,+300
```

must be paired on the same seeded initial condition.

Do not assign different initialization indices by horizon or delay.

## 3. Why Confirmatory Horizon–Delay Operating Envelope uses new seeds instead of Latency Calibration and Instrumentation seeds

This is deliberate.

The Confirmatory Horizon–Delay Operating Envelope purpose is to test whether the frozen Exploratory OOD–Delay Screening operating point is
locally stable on an **independent five-seed block** rather than merely reproducing
the six calibration seeds.

The Confirmatory Horizon–Delay Operating Envelope `25/+200` cells therefore act as an out-of-sample replication of the
calibrated operating point.

Do not replace Confirmatory Horizon–Delay Operating Envelope seeds with Latency Calibration and Instrumentation seeds solely to reuse rows.

## 5. Held-Out OOD–Delay Horizon Confirmation episode matching rule

Held-Out OOD–Delay Horizon Confirmation uses new held-out seeds:

```text
SEEDS = [14,15,16,17,18,19,20,21]
```

Therefore Held-Out OOD–Delay Horizon Confirmation does **not** repeat Exploratory OOD–Delay Screening episode seeds.

Instead, it repeats the Exploratory OOD–Delay Screening **experimental condition definition**:

```text
same base task
same exact LIBERO-Plus variant identity
same perturbation family
same RTC implementation
same Native/+200-ms delay definition
same checkpoint
```

Within each Held-Out OOD–Delay Horizon Confirmation condition, pair all horizons and delays by seed.

For fixed:

```text
task_key
variant_name
seed
scene ∈ {ID,OOD}
```

the following must share the same seeded reset state wherever the benchmark API
permits:

```text
n_action_steps = 20,25,30
delay = Native,+200
```

### ID versus OOD pairing

Do **not** require the OOD state to be geometrically identical to ID when the
perturbation itself changes geometry or robot initial state.

Instead match all **non-perturbed factors** and the seed.

Examples:

- `robot_initial_state`: different robot initial state is the perturbation; do not
  force it back to the ID state.
- `object_layout`: changed object layout is the perturbation; preserve that exact
  Exploratory OOD–Delay Screening variant.
- `light_conditions`: geometry/reset should otherwise match the seeded base task.
- `sensor_noise`: underlying task/reset should otherwise match; noise configuration
  remains exactly the frozen Exploratory OOD–Delay Screening variant.

## 7. Held-Out Object-Layout Cross-Task Replication object-layout cross-task matching rule

Held-Out Object-Layout Cross-Task Replication is a targeted post-Held-Out OOD–Delay Horizon Confirmation follow-up and reuses the Held-Out OOD–Delay Horizon Confirmation seed block:

```text

```

New OOD variants are exact frozen Exploratory OOD–Delay Screening identities:

|---|---:|---:|---:|---|
| `spatial_transport` | `1773` | `1772` | `3` | `pick_up_the_black_bowl_from_table_center_and_place_it_on_the_plate_add_15` |
| `goal_drawer` | `1891` | `1890` | `2` | `open_the_middle_drawer_of_the_cabinet_add_13` |

Within each fixed `(task, scene, exact variant, seed)`, all six
`{20,25,30} × {Native,+200}` cells must have the same initialization ID and
reset-state fingerprint. Do not require fingerprints to differ across seeds.

Object layout changes geometry, so ID and OOD fingerprints are not expected to
match. Pair them on seed, episode index 0, horizon, delay, checkpoint, RTC/timing
semantics, preprocessing, and all other non-perturbed factors.

Control reuse is asymmetric:

```text
goal_drawer ID: reuse 48 completed Held-Out OOD–Delay Horizon Confirmation rows exactly; do not rerun
spatial_transport ID: run 48 new Held-Out Object-Layout Cross-Task Replication rows on seeds 14..21
long_stove_moka: run nothing new; reuse completed Held-Out OOD–Delay Horizon Confirmation ID/OOD for synthesis
```

Held-Out Object-Layout Cross-Task Replication therefore executes 144 new episodes: 96 OOD + 48 spatial ID.

## 8. Initialization-State Audit rule

Initialization-State Audit is reset-only. For each of the three object-layout task pairs, audit
`initialization_index ∈ {0..7}` in both ID and exact frozen OOD scenes. Perform
three clean reset/fingerprint repetitions per task × scene × index.

Required gates:

```text
3/3 repeated fingerprints identical within each task/scene/index
8/8 fingerprints distinct across indices within each task/scene
requested index == resolved index; no fallback/wrap/clamp
```

ID and object-layout OOD fingerprints at the same index are not required to match
because object layout is the treatment. Initialization-State Audit outputs the frozen
`stage3c_validated_initializations.csv`; it contains no rollout seeds and no policy
outcomes.
