# CVPR strengthening plan

This document turns the four proposed paper-strengthening steps into a
reproducible checklist. The completed High-Power OOD–Delay Replication archive is the evidence base;
the remaining items are plans and must not be described as completed results.

## Step 1 — Make temporal coverage the mechanism, not just a label

Run `async_vla_benchmark/scripts/analyze_stage3_new_mechanisms.py` on the
64-seed episode CSV. Report success together with action age, RTC frozen-prefix
length, guided-overlap length, queue occupancy, and queue-underrun frequency.
The key claim should be limited to the observed association: added delay makes
executed actions older and changes the RTC action composition. Queue starvation
is cell-dependent, so it is not sufficient as a universal explanation.

## Step 2 — Test external validity with a second policy

The repository contains a preliminary OpenVLA-OFT native-8 diagnostic, but it
was not coverage-calibrated and is floor-limited on the long task. It should be
reported as preliminary provenance only. A publishable second-policy claim
requires an ID-only calibration, a policy-compatible executor, matched realized
coverage (not the same numeric horizon), fresh paired seeds, and the same
Native/+200-ms contrast. The generated `second_policy_protocol.csv` is a
planning artifact, not a completed experiment.

## Step 3 — Evaluate a coverage-aware controller ablation

The proposed controller should preserve a target queue headroom/coverage level
by changing refresh timing or the executed prefix. This is a new intervention,
not part of the frozen Held-Out OOD–Delay Horizon Confirmation evidence. Freeze the controller rule and all
thresholds on ID data, then evaluate it on held-out OOD tasks. Compare against
the fixed-coverage RTC baseline using success, action age, underrun rate, and
compute. The generated `coverage_controller_protocol.csv` records the design
space without claiming any result.

## Step 4 — Broaden the stress test and validation boundary

Use the generated `delay_coverage_sweep_protocol.csv` to pre-register a wider
delay/horizon grid. Keep task selection, seeds, and analysis fixed before
outcomes are inspected. If resources permit, add a genuinely held-out task or
a small hardware/second-simulator check; otherwise state clearly that the
paper remains simulation-only. Use complete-seed paired bootstrap intervals and
report failed or floor-limited cells.

## What is already complete

- 3,456 High-Power OOD–Delay Replication episodes: 64 fresh seeds (46--109), RTC, horizons 20/25/30,
  Native/+200 ms, three shared ID tasks and six frozen OOD candidates.
- Archive: `DataArchive/stage3_new_64_seeds/`.
- High-power interaction analysis: the existing High-Power OOD–Delay Replication analysis outputs.
- CPU-only queue/freshness analysis: generated by Step 1.

## What still needs GPU time

Only Steps 2--4 require new policy rollouts. The archive copy and Step 1
analysis require no GPU. Do not rent a GPU for the protocol manifests alone.

## Planning estimate on one A100-SXM4-40GB

These are deliberately conservative planning ranges, not measured guarantees.
They use the existing runbook's 40-hour allowance for a complete 3,456-episode
replication and include simulator/model startup overhead in the ranges.

| Step | Approximate episodes | GPU time | Non-GPU/setup time |
|---|---:|---:|---:|
| 1. Mechanism analysis | 0 | 0 | 5--15 minutes |
| 2. Second-policy diagnostic | 512 | 6--12 hours | 1--3 hours |
| 3. Coverage-aware ablation | ~2,300 | 20--32 hours | 2--4 hours |
| 4. Delay/coverage sweep | 4,800 | 35--55 hours | 2--4 hours |

Running all three new GPU studies sequentially is therefore roughly **61--99
GPU-hours**, plus **5--11 hours** of setup, validation, and analysis. A smaller
CVPR package should prioritize Step 1 immediately and Step 2 next; Steps 3 and
4 are optional expansion studies and should not be started without a frozen
runner and a separate compute budget.
